# Khao Fang: ตรวจและแก้คิวล้มเหลว 5 รายการ

## ขอบเขตและการอนุญาต

- ผู้ใช้สั่งวิเคราะห์ ทำต่อให้จบทั้งห้า และแก้โค้ดจริง. ภายหลังอนุญาตเริ่มทันทีโดยไม่รอพักเลนโพสต์ 35 นาที.
- ใช้ manual เฉพาะโปรเซสวินิจฉัยและรายชื่อทั้งห้า ไม่แก้เพดานถาวร/50 ต่อ 24 ชั่วโมง. ไม่ล้าง draft, ไม่เปลี่ยนผู้รับหรือข้อความที่ผู้ใช้เตรียมไว้.

## Why-Why จากหลักฐานจริง

1. สมบูรณ์หาไม่เจอ: DB เก็บชื่อเป็น `สมบูรณ์ วรรณใส 12 hours ago`; ตัว parser aria-label แยกเวลาเฉพาะ `เมื่อ`/`on` ไม่รองรับ suffix อังกฤษตรง ๆ. เมื่อเทียบชื่อเต็มกับมือถือจึงไม่มีวันตรง. อีกสามคนในโพสต์เดียวกันมีปัญหานี้ด้วย และชื่อจริงยังหลงอยู่ต้น body.
2. Bunriam, จรีรัตน์, จินดา เคยติด AccountUnreadable: โค้ดเก่าเปิด activity ที่ค้างอยู่. โค้ด fresh-start ที่แก้ก่อนหน้านี้ทดสอบจริงครั้งนี้อ่าน Khao Fang ผ่าน; dump guard เก็บไว้. ไม่มี XML ตอนล้มเก่าทุกครั้ง จึงไม่อ้างยืนยันเหตุแต่ละรอบย้อนหลังทั้งหมด.
3. Namtip เปิดโพสต์ได้จริง แต่ตรวจไม่ผ่าน: UI แสดงกลุ่ม `แชร์ตรงปกมาก shopee / lazada`, เจ้าของ Khao Fang และแคปชัน `กินแทนข้าวเย็นมา 1 เดือน…`; metadata ในฐานกลับเป็นชื่อแสดงผล `ลิงก์ที่สั่งเก็บ 2` ไม่มี caption. `_post_identity_visible` บังคับเทียบป้ายนี้เป็นกลุ่มจริง จึง reject ทั้งสอง route. หลักฐาน `diagnostics/target-reply-20260920-122920/009.xml`.
4. หลังแก้ชื่อ สมบูรณ์ผ่านชื่อบัญชี/โพสต์/แถว/marker `กำลังตอบกลับ สมบูรณ์ วรรณใส` และตรวจข้อความทั้งช่องก่อนส่งหนึ่งครั้ง. ภาพ UI ชั่วคราวแสดงคำตอบก่อนมีแจ้งเตือน ไม่ใช่หลักฐานส่งสำเร็จ.
5. อุปสรรคใหม่ที่ยืนยัน: `diagnostics/target-reply-20260920-123140/012.xml` ถึง `014.xml` แจ้ง `คุณไม่สามารถใช้ฟีเจอร์นี้ได้ในขณะนี้` พร้อมจำกัดจำนวนโพสต์/แสดงความคิดเห็นเพื่อป้องกันสแปม. เปิดใหม่ตรวจอย่างเดียว `target-reply-20260920-123423` ยังยืนยันคำตอบไม่ได้. ไม่มีการส่งซ้ำ และไม่ลองส่งอีกสี่คน.
6. ทำไมเว็บเดิมรายงานแค่ยืนยันไม่ได้: `fb_reply_safe.verify_on_phone` ตรวจเฉพาะคำตอบ ไม่เรียกตัวตรวจ restriction ที่มีในทางคอมเมนต์โพสต์แล้ว. จึงไม่บันทึก account hold และเสียเหตุผลจริงไป.

## การแก้โค้ด

- `fb_engagement`: แยก suffix เวลาที่มีรูปแบบชัดเจนออกจาก author; ใช้กับการอ่านใหม่/legacy threads/queued replies/บันทึก snapshot และ signature. รักษา comment_key/draft/submitted marker/receipt เดิม; การรวมแถวเลือกสถานะที่สำคัญก่อนและชื่อสะอาดเมื่อคะแนนเท่ากัน.
- `fb_engage`: normalize legacy ก่อนตรวจผู้รับ; read-only verification ของ submitted marker ไม่ต้องรอโควตาการส่ง. safety hold จาก Facebook มาก่อน hourly manual override จึงใช้ manual ฝืน restriction ไม่ได้.
- `facebook_group_post`: ป้าย manual ไม่ใช่ชื่อกลุ่มจริง; กรณีนี้บังคับเห็นหัวหน้าโพสต์เดี่ยว `โพสต์ของ <บัญชี>` เพิ่มจากชื่อเจ้าของ ก่อนอ่าน caption ไม่ยอมผ่านจากชื่อบน feed เฉย ๆ. กลุ่มจริงยังต้องเทียบเหมือนเดิม.
- `fb_reply_safe` + `fb_comment_guard`: ตรวจ restriction ก่อนพิมพ์ ก่อนกดส่ง และระหว่างยืนยัน; บันทึกหลักฐาน/พักบัญชีทันที และส่งเหตุผลเฉพาะกลับ ไม่กลืนเป็น timeout. เพิ่มข้อความที่เห็นจริงในรายการตรวจ.
- หน้าเว็บแสดง safety hold แม้คิวทุกแถวเป็น failed พร้อมบอกว่าระยะพักของระบบไม่ใช่คำรับรองเวลา Facebook ปลด. คำเตือนห้ามส่งซ้ำแสดงเฉพาะเมื่อมีรายการรอยืนยัน และแสดง error จริงของรายการนั้น.

## สถานะจริง (ไม่ถือว่าสำเร็จครบ)

- สมบูรณ์: กดส่งครั้งเดียว แล้ว Facebook แจ้ง restriction; submitted marker คงอยู่, sent_at ว่าง, ตรวจอย่างเดียวต่อได้ ห้ามส่งซ้ำ.
- Bunriam / จรีรัตน์ / จินดา / Namtip: ยังไม่ส่งในรอบนี้; คำตอบและคิวเดิมยังอยู่.
- บันทึก account guard Khao Fang เวลา 12:37:14 พักตามค่าเดิมของระบบ 12 ชั่วโมงถึง 21 ก.ย. 00:37:14. ไม่ใช่เวลาปลดจาก Facebook ซึ่งไม่ได้ระบุในแจ้งเตือน. Preaw ไม่มี hold เพิ่มจากเหตุนี้.
- โควต้าคิวตอบ Khao Fang ยัง 0/50 เพราะไม่มีคำตอบที่ยืนยันสำเร็จ. นี่ไม่ใช่ยอดการกระทำทั้งหมดบน Facebook: guard ของบัญชีมีคอมเมนต์สำเร็จจากทางอื่นวันนี้ 35 ครั้ง. ตัวเลขนี้ไม่พิสูจน์ว่า Facebook บล็อกเพราะถึง 35 หรือว่าตั้ง 50 แล้ว Facebook ต้องยอม.
- หยุดการส่งเพิ่มเติมเพราะข้อจำกัดแพลตฟอร์ม ไม่สลับบัญชี/ล้าง restriction เพื่อฝืนส่ง. ต้องตรวจว่าบัญชีกลับมาใช้ได้ก่อนดำเนินที่เหลือ.

## การทดสอบ

- 76 tests ผ่าน: identity parsing/legacy preservation, composer/receipt, account guard, caption, snapshot, priority, quota, expansion, stop/hide.
- Python compile และ `node --check web/engage.js` ผ่าน.
- ทดสอบมือถือจริงสมบูรณ์ก่อนแก้หาไม่พบ หลังแก้หา/marker ผ่าน; การส่งไม่ผ่านข้อจำกัดจริง จึงไม่อ้าง end-to-end สำเร็จ.
- เพิ่ม Chrome headless/API จำลอง 1 test ผ่าน (รวม 77) และเปิดใช้เซิร์ฟเวอร์ PID 151140 / version 53e210b5 แล้ว. API หลังรีสตาร์ตยืนยันชื่อสะอาด คำตอบเดิมทั้งห้ายังอยู่ และ safety hold ไม่กระทบ Preaw.

## หลักฐานโต้แย้งจากผู้ใช้หลังทดสอบ

- ผู้ใช้ส่งภาพ Khao Fang ตอบ Bunriam ด้วยข้อความ `.` หลังชื่อ mention. ภาพนี้ขัดกับข้อสรุปแบบเหมารวมว่าบัญชีตอบอะไรไม่ได้ทั้งหมด; ต้องจำกัดข้อสรุปก่อนหน้าให้แคบลง.
- ตรวจ `010.xml` ซ้ำ: ช่องตอบสมบูรณ์มีข้อความเดิมพร้อม Shopee และ Lazada สองลิงก์ครบ, พบปุ่ม `ส่ง` เพียงจุดเดียวที่ (672,1417). `012.xml` เป็นคำเตือนข้อจำกัดหลังส่งครั้งนี้จริง ไม่ใช่ข้อความเดาจาก timeout.
- หลักฐานจึงยืนยันได้เพียง “พบข้อจำกัดระหว่างส่งคำตอบนี้” ไม่ยืนยันว่าทั้งบัญชีถูกปิดทุกการโพสต์/ทุกคำตอบ. ข้อความ `.` ต่างจากคำตอบที่มีลิงก์และเป็นคนละเวลา จึงยังแยกไม่ได้ว่าขึ้นกับเนื้อหา/ลิงก์/จังหวะชั่วคราวหรือเงื่อนไขอื่น. ไม่ทดลองยิงข้อความอื่นเพื่อหลบข้อจำกัด.
- เวลาพัก 12 ชั่วโมงเป็นมาตรการของโค้ดเดิม ไม่ใช่ระยะเวลาที่ Facebook ระบุ. ภาพผู้ใช้ยังไม่ยืนยันผลของคำตอบสมบูรณ์เดิม; คง submitted marker และยังไม่ส่งซ้ำ. รอบตรวจโต้แย้งนี้อ่านหลักฐานเท่านั้น ไม่เปิดมือถือ ไม่ส่ง และไม่เปลี่ยน guard.
