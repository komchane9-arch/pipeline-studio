## Why-Why

1. ทำไมขึ้นยังไม่สำเร็จ? UI อ่าน reply_error เดิมของรายการที่ยังไม่มีผลสำเร็จ.
2. ทำไมยังพักอยู่? queued_replies เลือกเฉพาะ reply_error ว่าง จึงไม่ retry รายการล้มเหลวอัตโนมัติ.
3. ทำไมล้มตอนนั้น? ขั้น open_post_link ไม่ผ่านการยืนยันหน้าโพสต์ทั้งสองเส้นทาง จึงคืนก่อนค้นผู้รับ/พิมพ์คำตอบ.
4. ทำไมข้อมูลยืนยันไม่ครบ? เป็นลิงก์เก็บ manual: route สร้าง caption/group_id ว่าง และตั้งชื่อแสดงผล “ลิงก์ที่สั่งเก็บ N”. แคปชันของคิวมาจากผลลิงก์ในใบงานเท่านั้น; ไม่มีใบงานตรงลิงก์นี้จึงได้ _NO_META.
5. ข้อบกพร่องเชิงสาเหตุในโค้ดปัจจุบัน: เมื่อ caption ว่าง _confirm_linked_post ใช้ชื่อบัญชี+ชื่อกลุ่ม; _post_identity_visible เทียบ group_name กับข้อความบนจอจริง จึงนำชื่อสมมติ “ลิงก์ที่สั่งเก็บ 2” ไปใช้เสมือนชื่อกลุ่มจริง. เส้นทาง manual ไม่เติมตัวระบุจริงให้เส้นทางตอบมือถือ ทั้งที่เก็บคอมเมนต์ได้.

ยืนยันข้อบกพร่องข้อมูลและเงื่อนไขปัจจุบันได้ แต่ไม่มี screenshot/XML หรือสำเนาโค้ดขณะล้ม จึงยังไม่ยืนยันว่าข้อบกพร่องนี้เป็นสาเหตุเดียวของเหตุการณ์วันที่ 17 กันยายน ห้ามสรุปว่า Facebook ลบโพสต์/ล็อกอินหลุด/อินเทอร์เน็ตเสียจาก error รวมนี้.

## แนวแก้ที่เสนอ (ยังไม่ได้ดำเนินการ)

- เก็บ canonical post/group ID, ชื่อกลุ่มจริง, เจ้าของและแคปชันเมื่อรับลิงก์ manual; แยก display label ออกจาก identity.
- ยืนยันตัวตนโพสต์จากหลักฐานจริง ไม่ตัดการตรวจความถูกต้องเพื่อให้ผ่าน.
- แยกเหตุผลเปิดลิงก์ไม่สำเร็จกับเปิดได้แต่ยืนยันไม่ได้ และบันทึกภาพ/XML เมื่อผิดพลาด.
- ก่อนอนุญาต retry รายการเก่า ตรวจว่ามีคำตอบขึ้นจริงแล้วหรือไม่ โดยเฉพาะข้อมูลก่อนมี submitted marker.
- UI แสดงว่าเป็นความล้มเหลวเก่า และแสดงคำเตือน “ตรวจผลเท่านั้น ห้ามส่งซ้ำ” เฉพาะเมื่อ uncertain > 0; ปัจจุบันต่อท้ายแม้เป็น 0 จึงทำให้สับสน.
