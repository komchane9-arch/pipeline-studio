## 2. เจาะลึก 4 สายงานหลัก (The 4 Lanes)

### 2.1 สายโพสต์ Facebook (`post`)
- **หน้าที่:** สร้างโพสต์, ดึงสินค้า Shopee Affiliate, ยิงโพสต์ลงกลุ่ม Facebook ผ่านมือถือ, เช็กยอด, ตรวจสอบสุขภาพกลุ่ม
- **ไฟล์เจ้าของ:** `facebook_group_post.py` (253 KB), `fb_auto_post.py`, `fb_limits.py`, `fb_screen.py`, `publish_flow.py`, `shopee_*.py`, `web/post.js`
- **จุดชี้เป็นชี้ตาย:**
  - การโพสต์ต้องเป็นการกดหน้าจอจริงทุกจุด (ห้าม Deep-link ข้าม)
  - แย่งจอมือถือกับสายคลิปและสายเอนเกจเมนต์ -> ต้องผ่าน `phone_queue` เท่านั้น

### 2.2 สายเจนคลิปและลงวิดีโอ (`video`)
- **หน้าที่:** ดึงข้อมูลสินค้า, เขียนสคริปต์/สตอรี่บอร์ดด้วย AI (Gemini/ChatGPT), สังเคราะห์เสียงพูด (TTS), ตัดต่อวิดีโอ, เรนเดอร์คลิป และออโต้โพสต์ลง TikTok / Shopee Video
- **ไฟล์เจ้าของ:** `clip_app.py`, `flow_*.py`, `clip_*.py`, `gemini_*.py`, `tiktok_*.py`, `shopee_scrape.py`
- **จุดชี้เป็นชี้ตาย:**
  - มี 7 ขั้นตอนห้ามข้าม: ร่างบท -> ตรวจความถูกต้อง -> สังเคราะห์เสียง -> ตรวจคำอ่าน -> ผสานคลิป -> ตรวจคลิป -> โพสต์
  - ห้ามตัดสเปกหรือถอยไปใช้แบบคุณภาพต่ำเงียบๆ (Silent Fallback)

### 2.3 สายเก็บข้อมูลและวิเคราะห์ Big Data (`fb_mass` / `collector`)
- **หน้าที่:** สแกนหากลุ่ม Facebook แมส, เจาะเก็บโพสต์ย้อนหลัง 1,000 โพสต์ (Bot 8 & Bot 9), อ่านคอมเมนต์, วิเคราะห์ไวรัล, คำนวณ Engagement
- **ไฟล์เจ้าของ:** `fb_mass_bot.py`, `fb_mass_finder.py`, `fb_posts_collect.py`, `fb_posts_store.py`, `fb_posts_comments.py`, `data/fb_posts.db`
- **จุดชี้เป็นชี้ตาย:**
  - สองบอทเขียน SQLite พร้อมกัน -> ต้องมี `busy_timeout` และ retry
  - รูปภาพเก็บลง Google Drive `G:` -> ห้ามเขียนเร็วกว่าแคชบน C: อัปโหลดทัน (ด่าน `disk_ok()`)

### 2.4 สายระบบควบคุมกลาง & ฮาร์ดแวร์มือถือ (`main`)
- **หน้าที่:** Server Gateway, หน้าเว็บหลัก, จัดการคิวมือถือ, ตรวจจับการชนกันของแชท/คำสั่ง, บอทโปรไฟล์
- **ไฟล์เจ้าของ:** `app.py`, `studio_shared.py`, `devices.py`, `phone_queue.py`, `scrcpy_control.py`, `dispatcher.py`, `file_claims.py`, `orders.py`

## 3. สารบัญบทเรียนบั๊กใหญ่ในอดีต (The Wall of Past Bugs & Root Causes)

ตารางนี้คือสิ่งที่ **"แพงที่สุด"** ในโปรเจกต์นี้ รวบรวมจากประวัติการพังจริง เพื่อเตือนสติตัวเองก่อนแตะต้องโค้ด:

| รหัสบั๊ก / เหตุการณ์ | อาการที่แสดงออก | รากเหง้าที่แท้จริง (Root Cause) | บทเรียนและข้อป้องกันที่ต้องจำให้ขึ้นใจ |
| :--- | :--- | :--- | :--- |
| **`354819f` (สายโพสต์ตาบอดทั้งระบบ)** | ใบงาน 23 ใบและทะเบียนกลุ่ม 6 กลุ่มอ่านได้ 0 ทั้งที่ไฟล์จริงอยู่ครบบน Google Drive | เซิร์ฟเวอร์เขียนทดสอบไฟล์บน Drive พลาดเสี้ยววินาทีเดียวตอนบูต -> โค้ดถอยไปใช้โฟลเดอร์เปล่าเงียบๆ (`POST_DIR_READY` มีแต่ไม่มีใครตรวจ) | **ห้าม Silent Fallback เด็ดขาด!** เมื่อเชื่อมโยงปลายทางไม่สำเร็จ ต้อง Retry 3 ครั้ง และถ้าล้มจริงต้องแจ้ง Error ชัดเจน ห้ามถอยไปใช้ของเปล่าเงียบๆ |
| **`fb_kw_state` คำตัดสินหาย** | คำตัดสินที่กดเลือกกลุ่มผ่านหน้าเว็บ หายไปอย่างไร้ร่องรอย | `fb_mass_finder.save_kw_state()` เขียนทับไฟล์ JSON ทั้งดุ้นโดยไม่มี File Lock ขณะที่บอทถือไฟล์ในมือนานเป็นนาที -> เกิด Race Condition เขียนทับกัน | **ห้ามเขียนทับ State รวมของบอท!** แยกไฟล์คำตัดสินของผู้ใช้ออกมาต่างหาก (`fb_group_decisions.json`) ที่มีแต่เว็บเขียน บอทเขียนทับไม่ได้ |
| **ตัวเก็บข้อมูลตายกลางทาง (46%)** | บอท Bot8/Bot9 หลุดการทำงาน ข้อมูลค้างเป็น `running` ถาวร | 1) การจองกลุ่ม (Lease) สั้นกว่าเวลาทำงานจริง (เดิมตั้ง 3 ชม.แต่งานจริง 4-7 ชม.) ทำให้บอทอื่นแย่งงานซ้ำ<br>2) ข้อผิดพลาดเกิดนอกบล็อก `try-except`<br>3) ล็อกรวมกันสองบอททำให้ไล่ย้อนหลังไม่ได้ | 1) ตั้ง Lease Time ให้ครอบคลุมงานจริง (12 ชม.)<br>2) ทุกจุดเข้าถึงฐานข้อมูลต้องมี Error Guard และ Retry<br>3) ต้องติดแท็ก `[Bot8]` / `[Bot9]` ในทุกล็อก |
| **ปุ่ม ▶ บนหน้าเว็บ "ไม่ทำงาน" ทั้งที่ทำงาน** | คนกดปุ่มซ้ำๆ เพราะคิดว่าระบบค้าง | หน้าเว็บไม่แสดงสถานะ Loading/Running ให้ผู้ใช้เห็นทันที และตัวตรวจหน้าจอ `screen_changed` หลุดเฟรม | เมื่อผู้ใช้สั่งงาน ต้องมี Visual Feedback ทันที และตัวตรวจสถานะต้องดูของที่ **"มีเฉพาะตอนสำเร็จ"** ไม่ใช่ดูว่าไม่เจอของที่แปลว่าล้ม |
| **อ่านผังจอ `uiautomator dump` ไม่ได้ทั้งคืน** | ระบบค้างอยู่ที่ขั้นอ่านจอ ตอบกลับว่า `could not get idle state` | Android บนมือถือเปิด Window Animation ไว้ ทำให้หน้าจอไม่เคยนิ่ง (Never Idle) | ต้องปิด Animation บนมือถือทั้งหมด (`window_animation_scale 0`) ใน Pre-flight Check เสมอ |
| **ดิสก์ C: เต็มจนระบบพัง (Google Drive Buffer)** | พื้นที่ C: ลดลงอย่างรวดเร็วจนเหลือ 0 MB แม้ว่าจะสั่งเซฟรูปลงไดรฟ์ G: | ไดรฟ์ `G:` คือ Google Drive Streaming ซึ่งต้องใช้พื้นที่แคชบนไดรฟ์ `C:` ก่อนอัปโหลด ถ้าโหลดรูปเร็วกว่าเน็ตอัป แคชจะล้น C: | ต้องมีฟังก์ชัน `store.disk_ok()` ตรวจทั้ง C: และ G: หากเหลือน้อยกว่า Floor (4.0 GB) ต้องสั่งหยุดโหลดรูปทันที |
| **หน้าเว็บขาวโพลน (ESM TDZ Bug)** | เปิดหน้าเว็บไม่ติด ขึ้น Error ตัวแปร Uninitialized | มีการ Import โมดูลย้อนกลับลำดับ (เช่น core ไป import post) ทำให้ติด Temporal Dead Zone ใน JavaScript ESM | **ลำดับ Import ต้องเป็นเส้นตรงทิศทางเดียว:** `core.js` -> `phone.js` -> `post.js` -> `video.js` -> `boot.js` ห้ามย้อนศร |
| **Version Mismatch (หน้าเว็บกับเซิร์ฟเวอร์คนละรุ่น)** | หน้าเว็บกดฟังก์ชันใหม่แล้ว Error 404 หรือส่งพารามิเตอร์ไม่ตรง | แก้ไขโค้ด JavaScript/HTML แล้วไม่ได้รีสตาร์ตเซิร์ฟเวอร์ หรือเบราว์เซอร์ติดแคช | **กฎเหล็ก Server Update Rule:** แก้โค้ดเสร็จต้องรัน `restart_studio.py` และตรวจ Version Header / Cache-Control เสมอ |

## 4. กฎเหล็กที่ตนเองห้ามละเมิดเด็ดขาด (Engineering Golden Rules)

### 🔴 กฎข้อที่ 1: "ห้ามทำให้ระบบตาบอดเงียบๆ (No Silent Fallback)"
- หากโฟลเดอร์รูปภาพ, ฐานข้อมูล, หรือ Google Drive เข้าถึงไม่ได้ **ห้าม** เขียนโค้ดประเภท `except: pass` แล้วถอยไปใช้ค่าว่างหรือโฟลเดอร์ชั่วคราวโดยไม่แจ้งเตือน
- ต้อง Fail Fast หรือขึ้น Alert ให้มนุษย์เห็นทันที

### 🔴 กฎข้อที่ 2: "ตรวจความสำเร็จจากสิ่งที่มีจริง ไม่ใช่ตรวจจากการไม่เจอ Error"
- การเช็กว่าโพสต์สำเร็จ **ห้าม** ดูแค่ว่า "ไม่เจอคำว่า Error"
- **ต้องตรวจหา:** URL ของโพสต์ใหม่, ปุ่มแชร์ที่ปรากฏ, หรือรหัสโพสต์ที่เปลี่ยนไปจริงๆ เท่านั้น

### 🔴 กฎข้อที่ 3: "ทรัพยากรที่มีชิ้นเดียว ต้องผ่านคิวเสมอ (Exclusive Hardware Locking)"
- **มือถือแต่ละเครื่องมีจอเดียว:** สายโพสต์, สายคลิป, สายคอมเมนต์ ห้ามแย่งกันเข้า ADB เด็ดขาด ต้องผ่าน `phone_queue.db` ด้วยคำสั่ง `ticket = queue.acquire(...)` เท่านั้น
- **SQLite มีไฟล์เดียว:** สองบอทเขียนชนกันได้เสมอ ต้องเปิดใช้ `PRAGMA busy_timeout=60000` และครอบด้วย `db_retry` เสมอ

### 🔴 กฎข้อที่ 4: "อย่าเดาโครงสร้างข้อมูล ให้ดูของจริงในไฟล์/ฐานข้อมูลก่อน"
- ในอดีตเกิดบั๊กหลายครั้งจากการเดาว่าข้อมูลเป็น Dict (เช่น `data.get('groups')`) แต่ของจริงเป็น List หรือสคีมาของตารางไม่มีคอลัมน์นั้น
- **ต้อง:** ตรวจสอบโครงสร้างจริงด้วยการ inspect schema ก่อนลงมือเขียนโค้ดเสมอ

### 🔴 กฎข้อที่ 5: "แก้ไขหน้าเว็บเสร็จ ต้องรีสตาร์ตเซิร์ฟเวอร์และบันทึกประวัติเสมอ"
- การแก้ไฟล์ใน `web/` หรือ API ใน `app.py`:
  1. ตรวจไวยากรณ์ก่อน (`node --check` หรือ `python -m py_compile`)
  2. รันสคริปต์รีสตาร์ตเซิร์ฟเวอร์ (`restart_studio.py`)
  3. บันทึกงานลงใน `note/WEB-WORK-LOG.md` (เรียงตามเวลา ห้ามลบทับของเก่า)
  4. สรุปภาพรวมลงใน `note/WEB-SYSTEM-SUMMARY.md`

## 5. แผนผังการทำงานและจุดตรวจ (Pre-Flight Checklist สำหรับตัวเอง)

ก่อนลงมือแก้โค้ดหรือส่งงาน ให้ท่องเช็กลิสต์ 5 ข้อนี้ในใจทุกครั้ง:
```
[ ] 1. เข้าใจปัญหาถึงระดับ Root Cause แล้วหรือยัง? (ไม่ใช่แค่แก้ดักหน้าจอชั่วคราว)
[ ] 2. มีการเรียกใช้ฟังก์ชันเดิมที่มีอยู่แล้วหรือยัง? (หลีกเลี่ยง Duplicate Logic)
[ ] 3. จุดที่แก้ มีผลกระทบข้ามสายงาน (Lanes) หรือไม่? (Post vs Video vs Main)
[ ] 4. โค้ดที่แก้รองรับกรณีล้มเหลว (Edge Cases & Fallbacks) อย่างถูกต้องและโวยวายเมื่อพังหรือไม่?
[ ] 5. ได้รันเทสอบจริงและรีสตาร์ตเซิร์ฟเวอร์ตรวจสอบพอร์ตตอบกลับ 200 แล้วหรือยัง?
```
