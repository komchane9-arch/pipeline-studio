## เปรียบเทียบและ Why-Why

- ใช้ตัวตรวจเดิม fb_engage.run_queued_reply → _find_queued_comment(require_reply=False) → fb_reply_safe.verify_on_phone_result. รอบนี้เพิ่มเก็บ PNG/XML/บริบททุก dump ด้วย evidence.capture และอ่านภาพด้วยตาเทียบ log; ไม่เปลี่ยนเกณฑ์ matching.
- เกณฑ์เดิมยังตรวจ parent ชื่อ+ข้อความ, การเยื้องของคำตอบ, ชื่อบัญชี, ข้อความ และ URL ครบในแถวเดียวกัน. วันนี้ผ่านรายการ 2 และไม่ผ่านรายการ 1 สอดคล้องภาพ.
- เหตุที่รายการ 2 ไม่ฟื้นเอง: mark_reply_submitted ตั้ง reply_error เป็นข้อความไม่ยืนยันก่อนแตะปุ่มจริงเพื่อกันซ้ำ; queued_replies เลือกเฉพาะ reply_error ว่าง. เซิร์ฟเวอร์ดับก่อนบันทึกผล ทำให้สถานะไม่ยืนยันถูกกันออกจากคิวอัตโนมัติ. ปุ่มตรวจผลด้วยมือยังเป็นทางเข้าได้.
- เหตุที่ข้อความหน้าเว็บชวนเข้าใจผิด: receipt ถูกบันทึก BEFORE irreversible tap ใน send_reply จึงยืนยันได้เพียงเริ่มพยายามส่ง ไม่ใช่ Facebook รับแล้ว. รายการ 1 เจอ FacebookRestricted จริง แต่ข้อความล่าสุดถูกผลตรวจซ้ำ reply_not_in_thread แทน ทำให้เหตุเริ่มต้นไม่เด่นในหน้าเว็บ.

## แนวแก้เสนอ รอผู้ใช้ก่อนดำเนินการ

1. คืนรายการ 2 ผ่านทางตรวจผลเดิมเพื่อบันทึกสำเร็จจากหลักฐานจริง ไม่ส่งใหม่.
2. แยกคิวตรวจผลแบบอ่านอย่างเดียวของรายการ submitted-but-unconfirmed ให้กู้หลังเปิดเซิร์ฟเวอร์ได้ มีเพดานและพัก ไม่เข้าทางส่งซ้ำ.
3. แสดงพยายามส่งแล้ว/ยืนยันสำเร็จ/ตรวจถูกขัดจังหวะ/พบข้อจำกัดแยกชัด และรักษาเหตุเดิมคู่ผลตรวจล่าสุด.
4. รายการ 1 คงสถานะไม่ยืนยันไว้; การส่งใหม่ต้องตัดสินใจต่างหาก ไม่อนุมานจากการหาไม่พบครั้งเดียว.

หลังตรวจ API ยืนยัน reply_sent_at ของทั้งสองยังว่างและ receipt/error เดิมยังอยู่. ไม่มีการแก้โค้ดหรือ restart.
